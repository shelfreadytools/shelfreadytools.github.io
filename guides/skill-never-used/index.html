Claude Code skill installed but never used? What decides it, tested

21 fresh Claude Code sessions: when Claude used an installed skill and when it ignored it. The folder it sits in, its name and description, and front matter Claude Code cannot read. Claude Code 2.1.325.

Before Claude picks a skill, all it has is one line per skill: the skill's name and its description, in the listing Claude Code gives it. If that line does not say what the skill is for, or the skill is not in the listing at all, the skill is not used, and nothing reports an error.

We ran the same small skill, a release-notes writer, in seven versions, each in three fresh claude -p sessions on Claude Code 2.1.325 (16 November 2026), with no other skills, settings or MCP servers of ours loaded. The project was a git repository with four commits after a v1.0 tag, and the prompt each time was "Write release notes for everything since v1.0." "Used" means Claude called the Skill tool; the listing line is read from each session's transcript, so it is exactly what Claude saw.

What it shows

1. The folder. Claude Code 2.1.325 does not read .agents/skills/: the skill was never listed, in three sessions out of three. Project skills go in .claude/skills/<name>/SKILL.md, personal ones in ~/.claude/skills/<name>/SKILL.md, or in a plugin's skills/ folder. Support for .agents/skills/ is an open request.

2. The name and the description work together. A name that says the job, release-notes, was used even with a vague description. A generic name, helper, was used only when the description said what it does. Do not count on the name: write a description that would work alone, with what the skill does and when to use it ("Use when the user asks for release notes, a changelog entry...").

3. Front matter Claude Code cannot read. Then the listing falls back to the folder name and the first heading of the file, here helper: Helper, and the skill was never used. Which errors do that is not obvious. In a separate session with eight broken variants side by side (the probe), Claude Code:

  • read an unquoted : in a value ("description: Writes meeting notes: who came, ...") as intended, although a YAML parser refuses it;
  • also recovered an unclosed quote when the value contained : , stray quote included (the last row above);
  • fell back to the first heading for an unclosed quote without : , a tab before a key, a description written as a list, a missing description, and a file with no front matter.

Claude Code's documentation describes the fallback for a missing description ("the first non-empty line of the markdown content"); the probe shows it also applies to front matter it cannot read. So the only reliable test is to look at the line Claude sees.

See the line Claude sees

Every claude -p session writes a transcript to ~/.claude/projects/<project folder>/<session id>.jsonl. The skill listing is the entry whose attachment.type is skill_listing: one - name: description line per skill. A quick check from the project folder:

claude -p "Reply with only the word OK." --output-format stream-json --verbose

The first event ("subtype": "init") has a skills list. In the probe, the skills whose description came from the front matter were in it, and the ones that fell back to a heading, or had no description, were not; a skill missing from that list is worth a look. The session_id in the same event names the transcript to open for the full listing line. In an interactive session, /skill-doctor lists the skills in the listing that have never been invoked.

The SR210 note is a false alarm: RELEASE_NOTES.md is the file the skill writes, not one it reads. The checker cannot tell whether a skill will be used; it can tell you the description gives Claude little to go on, and that the front matter will not be read as written. It does not look at where the skill is installed.

Limits

One prompt, one skill installed at a time, three sessions per version and the default model. With many skills installed, Claude Code keeps every name but drops some descriptions to fit the listing's character budget, and it cuts each entry at 1,536 characters (its skills documentation); vaguer prompts leave more to chance. Treat these results as the easy case: a skill that fails here will fail in real use.
